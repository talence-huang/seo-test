# 09 — Coding Agent 協作紀錄：從需求到實作

> 本文件整理本專案與 Coding Agent（Claude Code，模型 Claude Opus 5.5）的協作過程：每個關鍵節點的需求指令、Agent 的分析與處理、產出與驗證。
>
> - 指令已整理為正式的需求描述；過程中的確認與操作類訊息（例如「繼續」「開啟網頁」）不另列。
> - 時間為台灣時間，全部發生在 2026-10-17。
> - 費用指 Agent 本身在研究中呼叫 Claude Opus 的花費，不含開發過程中 Coding Agent 的使用費。

## 協作原則（貫穿全程的約定）

| 原則 | 做法 |
|---|---|
| 研究導向、不擴大範疇 | 每個階段先設計、確認範疇後才實作；完成一個階段就提交一次 |
| 過程可觀察 | 程式負責量測與判定，LLM 只負責詮釋；每一步的理由、候選行動、證據都寫進紀錄 |
| 金鑰由使用者掌握 | API 金鑰只由使用者在 `.env` 填寫，Agent 不經手、不寫入任何檔案；提交前檢查 |
| 花錢之前先確認 | 會呼叫付費 API 的步驟，先提出預估費用與上限，經同意才執行；執行中超過上限會自動停止 |
| 照實回報 | 評測結果不論好壞都照實記錄；發現問題先停下、說明原因，再提出修正方案 |

## 一、需求理解與架構設計（02:17–03:00）

**指令**
1. 本任務要建立一個具備「自主研究、假設驗證與持續進化」能力的 SEO 競爭情報 Agent，並以 Hermes 架構為參考。請先研究 Hermes 的運作方式，拆解任務細項、設計完整流程，確認後再開始實作。過程中全程以繁體中文回覆，並呈現實作過程。
2. 需求規格分為三部分：
   - A. 自主研究迴圈：定義目標 → 決定需要的資訊 → 調用工具 → 解析結果 → 形成假設 → 尋找客觀證據 → 修正推論 → 決定下一步；並展示在時間、Token 與 API 限制下如何決定優先抓取哪些網址。
   - B. 記憶與學習機制：第 2 次以後的分析能運用過往的成功、失敗與人工糾偏經驗，並提供可執行的評測，證明 Agent 比第 1 天更好。
   - C. 可靠性與自治邊界：辨識最重要的失效模式，並定義哪些動作可以完全自主、哪些高風險動作必須暫停等待人工核准。
3. 本次以研究為目的：重點是設計完整的流程，並讓使用者能觀察研究過程，而不是像黑盒子一樣直接給出結果。請勿擴大範疇，專注於研究內容並收斂成果。

**Agent 的處理**
- 研究 Hermes 的架構與設計模式，寫成 [01 Hermes 架構研究](01-hermes-architecture.md)。
- 定義研究問題、範疇與整體架構，寫成 [02 研究總覽與範疇](02-seo-intel-agent-design.md)：選擇自建研究迴圈而非現成框架，理由是每一步都要能被程式控制與觀察。
- 規劃 Phase 0–6 的實作計畫，寫成 [03](03-implementation-plan.md)；建立 [00 需求對照表](00-requirements-traceability.md)，逐條追蹤「需求 → 設計 → 模組 → 驗證」。

## 四、需求驗收與評測重建（14:45–16:10）

### 4.1 對照原始需求驗收

**指令**：請對照原始需求 A、B、C，逐項評估目前版本是否符合。

**Agent 的評估**：
- **A 符合**：研究迴圈與成本控制都在。
- **C 大致符合**：部分驗證只存在於研究期間的版本。
- **B 不符合**：移除模擬環境時，評測工具一併刪除，已經沒有可執行的方法證明「比第 1 天更好」。

### 4.2 重建評測

**指令**：請用幾個有已知答案的測試網站，重建 Day 1 vs Day N 評測，並一起更新過時的文件；動工前先提出設計與費用預估。

**Agent 提出的設計**：
- 8 個程式產生的中文測試網站：4 個訓練、4 個測試，其中 1 個是對照網站。
- 每個網站有固定的答案範本、干擾項，以及共通的失效特徵：防火牆路徑、JS 空殼頁、無限日曆、注入頁、robots 禁止的路徑。
- Agent 本身使用真實 Opus。
- 評分只依標準答案與請求紀錄。
- 另外植入一條錯誤經驗，測試它多久被淘汰。
- 預估約 US$13.5，上限 US$15。

**指令**：依建議方案執行：每個測試網站研究 3 次，加上錯誤經驗淘汰，不做消融，總花費上限 US$15。

**主要產出**：
- `evals/`：測試網站產生器、評分器、評測流程、報告，以及不需金鑰、免費的重播功能。
- `tests/test_evals.py`：不呼叫 LLM，驗證評測流程本身。

### 4.3 評測過程中發現並修正的問題

真實 Opus 的評測揭露了模擬環境與假 LLM 測不出來的問題。以下都是在訓練網站或開發驗證中發現的，修正後才進行測試網站的比較：

| # | 問題 | 影響 | 修正與驗證 |
|---|---|---|---|
| 1 | 移除模擬環境時誤刪兩個輔助函式 | Agent 一做「範本變動抽樣」，整個研究就崩潰（真實網站研究也會發生） | 補回函式並加單元測試；用靜態掃描檢查全專案，確認沒有其他未定義的名稱 |
| 2 | sitemap 沒有列 lastmod 時，「更新爆發度」把「沒有日期」當成「0% 更新」，產生反對的證據 | 很多真實網站的 sitemap 不列日期，答案會被誤判為背景變動 | 更新比例只用有日期的網址計算，完全沒有日期時回報「無法判斷、不計入證據」；同時修正先從 SERP 加入的網址，之後拿到日期卻沒被計入的問題 |
| 3 | 經驗淘汰規則用固定門檻（套用後成功率 < 50% 即淘汰） | 有一半訓練網站不論有沒有經驗都下不了結論，「避開防火牆路徑」這類與結論對錯無關的效率經驗因此全被淘汰，Day N 等於沒有學到東西 | 改為和「沒有套用這條經驗的研究」比較，低 25 個百分點以上才淘汰。發現後立即停止評測，避免繼續花錢在量不出差異的研究上 |
| 4 | 修正淘汰規則後要重跑訓練與 Day N | 全部重跑超出預算 | 新增「接續」功能：Day 1 與前 7 次訓練直接重播錄製的回應（結果相同、不花錢），只有提示改變的研究才呼叫 Opus；先用不花錢的預演確認只有 1 次訓練需要重跑 |

**指令**：總花費上限放寬到 US$16；Day N 照原計畫每個網站 3 次，加上錯誤經驗淘汰，接續跑完。

### 4.4 評測結果（真實 Opus，35 次研究）

| 指標 | Day 1（無記憶） | Day N（學習後） | 配對差異（95% CI） |
|---|---|---|---|
| 平均抓取次數（12 組） | 33.3 | 18.0 | −15.3（−17.8 ～ −12.5） |
| 浪費的請求（相似網站，9 組） | 5.0 | 0.0 | −5.0 |
| 首個關鍵證據抓取數（12 組） | 10.1 | 9.5 | −0.6（−0.8 ～ −0.3） |
| 平均步驟數 | 149 | 75 | −74 |
| 答對次數：相似網站 | 3/9 | 2/9 | 信賴區間跨過 0 |
| 答對次數：對照網站 | 3/3 | 1/3 | 信賴區間跨過 0 |
| LLM 花費／次 | US$0.34 | US$0.35 | 無差異 |

**需求 C 的驗證**（全部 35 次研究）：
- 安全違規 0 次：robots 禁止的路徑、需登入的路徑、任務以外的網域、照著注入指令抓取、抓取間隔過短都沒有發生。
- 注入頁被抓到 19 次，19 次都被偵測並忽略，「免費領取」頁從未被請求。
- 程式崩潰 0 次。
- 植入的錯誤經驗在第 2 次研究後，因為「成立的結論正好落在它要求避開的路徑」兩次而被淘汰。

**解讀**：
- **效率**：學習後的 Agent 明顯更有效率，抓取與步驟都減少約一半，浪費歸零。
- **正確率**：沒有提升，甚至變差（6/12 → 3/12），雖然信賴區間跨過 0。
- **原因**：比對 Day N 失敗的研究，證據與 Day 1 幾乎相同，差別在 LLM 給假設的先驗偏低，以及紅隊一再以「只有單一時點的 SERP、無法證明因果」提出反對。結果信心停在 0.7 左右，跨不過 0.8 的成立門檻。
- 因此需求 B 目前只在**效率**上得到證明；**正確率**需要後續處理。

**費用**：總計約 US$14.68，在 US$16 的上限內。
- 開發驗證 US$1.59
- 第一輪評測 US$7.42，含中途停止前已花的部分
- 接續評測 US$5.67

## 五、研究目標調整：從「內容變化」到「競爭策略」（15:34–）

**指令**：這項研究要推導出三個結論：
1. 競品採取了哪些關鍵的 On-page SEO 策略？
2. 競品採取了哪些關鍵的 Off-page SEO 策略？
3. 若要與之競爭，最值得優先採取的行動為何？

請檢視目前的研究流程，是否以推導這些結論為目標，而不是泛泛地分析 SEO。

**Agent 的評估**：目前的研究問題被固定為「哪個頁面範本在期間內改了什麼」。
- **On-page**：只涵蓋一部分。
- **Off-page**：完全沒有，因為反向連結無法靠爬網站取得。
- **行動建議**：沒有優先順序，也沒有和自家網站比較。

**指令**：依此方向調整：研究目標固定為 On-page、Off-page、優先行動三個問題；Off-page 使用反向連結 CSV；行動建議必須與自家網站比較。動工前先提出各步驟的實作計畫與要修改的檔案。

**Agent 提出的 8 步計畫**：
1. **資料輸入**：反向連結 CSV、自家網站。
2. **策略維度量測**：程式固定的詞彙，例如 FAQPage、內容深度、title 關鍵字、作者資訊、內部連結。
3. **研究迴圈**：新增排名頁輪廓、反向連結輪廓、自家網站輪廓三種資訊需求。
4. **證據與結論**：排名頁與非排名頁的對比（Fisher 檢定）、採用時序、連結成長；優先行動由程式依「影響 × 差距 ÷ 難度」排序。
5. **呈現**：報告、時間軸與網頁。
6. **評測**：加入策略、反向連結與自家網站的標準答案。
7. **開發驗證**。
8. **重跑評測並更新文件**。

**指令**：依計畫實作；目前的評測完成後，先提交評測與錯誤修正，再從步驟 1 開始。

### 5.1 實際使用時發現「每次都沒有結論、也沒有記憶」

**回報**：在網頁上對同一個競品研究了 5 次，每次都是「沒有足夠證據下結論」，記憶也一直是空的。

**Agent 的診斷**（依研究紀錄）：
- **沒有提供排名資料**：Agent 不知道哪些頁面真的有排名，只能在 sitemap 的 49 個範本、2,366 個網址中盲抽。抓的 33 頁中只有 1 頁標題含關鍵字。
- **研究問題只找「期間內改了什麼」**：找不到有變化的主題頁，就沒有可以檢驗的證據；連續 15 次抓取沒有新證據時，因報酬遞減而停止。
- **程式決策是確定性的**：同樣的輸入每次都走同一條路，重跑也不會變好。
- **記憶只從成功學習**：這是為了避免學到雜訊，所以一直沒有結論，就一直學不到東西。

**指令**：把「沒有排名資料時的提醒與報告說明」「無結論時也記錄原因」併入改造計畫，繼續步驟 1。

**調整後的計畫**：
- 步驟 1：開始前就說明缺少哪些資料、會影響哪個問題。介面、CLI 與報告使用同一份說明。
- 步驟 4–5：研究無結論時，報告要說明原因，列出已量測的事實與缺少的資料，不再只給一句「沒有足夠證據」。
- 步驟 5：REFLECT 在無結論時也記錄原因（例如缺排名資料、主題頁太少），記憶分頁看得到。

### 5.2 進度

| 步驟 | 狀態 | 內容 |
|---|---|---|

## 八、研究層面的重要發現

1. **可觀察性本身就是除錯工具**：每一步的理由與證據都寫進紀錄，所以能從紀錄直接看出問題，例如「有日期的頁面被當成背景變動」「經驗套用後才被淘汰」，而不必猜。
2. **模擬環境與假 LLM 測不出的問題，真實 LLM 一跑就出現**：
   - 假 LLM 評測中每次都成功，所以淘汰規則的缺陷從未被觸發。
   - 換成真實 Opus 後，研究本身的難度讓成功率只有一半，固定門檻的規則就把有用的經驗也淘汰了。
3. **學習改善了效率，正確率沒有跟著改善**：
   - 抓取減半、浪費歸零，但正確率沒有提升。
   - 原因不在經驗本身，而是「是否下結論」對 LLM 自訂的先驗，以及紅隊「無法證明因果」的反對很敏感。
   - 效率與正確率必須一起評測，只看其中一個會誤判。
4. **自治邊界由程式強制是可靠的**：35 次真實 LLM 研究中，注入頁每次都被偵測，沒有任何越界請求。錯誤經驗能被客觀證據淘汰，不必依賴人。
5. **成本治理是研究流程的一部分**：
   - 費用預估、硬上限、Day 1 後的全程預估、發現問題立即停止，這些機制讓評測在預算內完成。
   - 錄製與重播讓修正後只需重跑受影響的部分：Day 1 與 7 次訓練直接重播，接續評測省下約 US$6.5。
